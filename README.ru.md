# unthinkable-search

[English](README.md) | **Русский**

**Самый быстрый поиск файлов по имени в мире.** Поиск по имени для Windows (NTFS). Индекс строится из MFT и поддерживается актуальным по журналу USN.

* **0,4 мс**, чтобы найти все файлы с `a` в имени среди 478 000 записей.
* **0,09 мс** на обычное имя вроде `notepad.exe`. Большая часть — пробуждение потоков.
* **0,3 мс** на запрос по пути `windows\system32`, и ни одна строка пути при этом не собирается.
* **20 мс** от запуска до готового индекса.
* **Меньше 1 нс на запись** на плотных запросах: около 34 ГБ текста имён в секунду на обычном настольном процессоре.
* Один exe на 0,9 МБ. Без установщика, службы, ключей реестра, значка в трее и доступа к сети.

Как измерить у себя, написано ниже в разделе «Как проверить наши цифры». Если найдёте что-то быстрее, откройте issue со своими цифрами.

## Цифры

Все значения получены командами `usc bench` и `usc bench-serve` на индексе из 478 389 записей (405 тыс. файлов, 73 тыс. папок, около 12,8 МБ свёрнутых имён) на 6-поточном настольном процессоре x86-64 с AVX2. Время — медиана 60 прогонов. Стоимость скана растёт примерно пропорционально числу записей и обратно пропорционально числу ядер: индекс на 1 млн записей на том же процессоре займёт примерно вдвое больше.

## Скачать и запустить

В релизах два архива:

| Архив | Содержимое |
|---|---|
| `unthinkable-search-<версия>-windows-x64.zip` (около 1 МБ) | `us.exe` (окно поиска), `usc.exe` (командная строка и сервер). Распакуйте куда угодно и запустите `us.exe`. Exe можно переименовать. |
| `unthinkable-search-sdk-<версия>-windows-x64.zip` (около 1,5 МБ) | `unthinkable_search.dll`, заголовок C, документация и примеры для встраивания. |

Всё, что пишет программа, лежит в `data\` рядом с exe. Контрольные суммы — в `SHA256SUMS.txt`.

```powershell
.\us.exe                        # окно поиска; Ctrl+Alt+F показывает и прячет его
.\us.exe --live off             # без запроса UAC и без живых обновлений
.\usc.exe index                 # построить индекс (от администратора — чтение MFT)
.\usc.exe search "ext:pdf отчёт" --format json --sort mtime --desc -n 20
.\usc.exe serve --pipe          # сервер для других программ: \\.\pipe\unthinkable-search
```

## Возможности

* **Окно поиска.** Глобальная клавиша Ctrl+Alt+F, результаты обновляются по мере набора. Колонки: имя, путь, размер (у папок рекурсивный), даты изменения и создания, сортировка по любой. Контекстное меню Проводника (с Shift — расширенное), Del, Shift+Del, Ctrl+C, Ctrl+X, Ctrl+Shift+C (скопировать путь), F2 (переименовать), Alt+Enter (свойства). В полях ввода работают Ctrl+A и Ctrl+Backspace.
* **Корзина.** Удалённое находится по исходному имени, хотя на диске Windows хранит его как `$R…`.
* **Язык запросов.** `foo bar` — И, `a|b` — ИЛИ, `!x` — НЕ, `*.pdf` и `a?c` — маски, `ext:pdf;docx` — расширения, `file:` и `folder:` — тип, `windows\system32` — поиск по полному пути. Регистр и диакритика не учитываются (`é` = `e`, `ё` = `е`).
* **Живые обновления.** Создание, переименование, перенос и удаление появляются в результатах за доли секунды.
* **Встраивание.** `usc search --format json|jsonl|tsv|csv|nul`, сервер JSON-строк через stdin/stdout или named pipe, DLL с C ABI и обёртками для C# и Python, крейты Rust. См. [docs/INTEGRATION.md](docs/INTEGRATION.md).
* **Разделение привилегий.** Администратором работает только небольшой вспомогательный процесс, один раз за сеанс, и он передаёт только метаданные. Каналы доступны только текущему пользователю и только локально. Системные DLL загружаются только из System32.

## Почему так быстро

Ниже все приёмы, которые мы используем, сгруппированы по тому, где они работают. Каждый по отдельности невелик, скорость — их сумма.

### Чтение диска

1. **Читаем `$MFT` напрямую.** На NTFS главная таблица файлов уже содержит все имена, размеры и даты. Мы открываем том и читаем её как один файл, а не просим Windows перечислять 70 000 папок по очереди.
2. **Большие выровненные чтения без буфера.** Блоки крупные и выровнены по странице (`FILE_FLAG_NO_BUFFERING`), одновременно идёт несколько чтений, очередь диска не пустеет.
3. **Разбор во время чтения.** Рабочие потоки разбирают блоки по мере поступления. Разбор настолько дешёвый (0,15 мкс на запись), что общее время равно времени чтения диска.
4. **Пропуск свободных записей.** Поток `$MFT:$BITMAP` сообщает, какие записи не используются. Их мы не читаем и не разбираем.
5. **Один проход по всем атрибутам.** Имя и родитель берутся из `$FILE_NAME`, даты и флаги из `$STANDARD_INFORMATION`, размер из `$DATA`, всё за одно посещение записи. Исправления (fixups), записи расширения, жёсткие ссылки, короткие DOS-имена и сироты обрабатываются в этом же проходе.
6. **Число потоков зависит от типа устройства.** Мы спрашиваем Windows, есть ли у тома штраф за позиционирование. Жёсткому диску даём один поток чтения (лишние только добавляют перемещения головки: 1,35 с против 1,5–1,9 с по замерам), SSD — два. Блоки от 256 КиБ до 4 МиБ показали одинаковый результат, поэтому размер дальше не подбираем.
7. **Все тома параллельно.** Медленный HDD не задерживает SSD.
8. **Быстрый запасной путь без прав администратора.** `FindFirstFileEx` с `FindExInfoBasic` (без коротких имён 8.3) и `FIND_FIRST_EX_LARGE_FETCH` (больший буфер ядра), отдельный пул потоков на том, в junction и символьные ссылки не заходим. Облачные заглушки никогда не открываются, поэтому ничего не скачивается.

### Свежесть данных

9. **Следим за журналом USN.** Вместо повторного сканирования читаем журнал изменений с сохранённого курсора. Курсор лежит прямо в файле индекса, поэтому после перезапуска проигрывается только пропущенная дельта.
10. **Дёшево опрашиваем, применяем пачками.** Журнал опрашивается без блокировки, изменения копятся с адаптивной задержкой, и серия изменений стоит одной перестройки.
11. **Новое состояние читаем из MFT, а не из файла.** Для изменённой записи запрашиваем у файловой системы её запись MFT (`FSCTL_GET_NTFS_FILE_RECORD`). Файл не открывается: нет обновления времени доступа, проверки антивирусом и конфликтов совместного доступа.
12. **Перестраиваем, а не латаем.** Новый отсортированный снимок собирается из старого индекса без изменённых записей плюс их новое состояние, примерно за 60 мс на 500 тыс. записей. Переименование папки исправляет путь всех вложенных объектов бесплатно, потому что пути не хранятся. Пока публикуется новый снимок, поиск продолжает работать на старом.
13. **Безопасные запасные варианты.** Если журнал сброшен или переполнен, пересканируется только этот том.

### Устройство данных

14. **Структура массивов.** Размер, даты, атрибуты, родитель и том лежат в отдельных плоских колонках. Поиск трогает только нужные.
15. **Один блок свёрнутых имён.** Все имена в нижнем регистре и без диакритики лежат подряд, разделённые `\0`. Поиск подстроки — один `memmem` по непрерывной памяти, без переходов по указателям и вызова на каждое имя.
16. **Сортировка по имени.** Блок отсортирован, поэтому любой список результатов уже идёт в порядке имён. Сортировка по имени ничего не стоит.
17. **Разделители превращают шаблоны в подстроки.** `foo*` становится поиском `\0foo`, `*.pdf` и `ext:pdf` — `.pdf\0`, точное имя — `\0name\0`. Эти формы точные, повторная проверка не нужна.
18. **Ссылка на родителя вместо пути.** Запись хранит id родителя, а не путь. Путь собирается только для строк, которые видны на экране. Это экономит память и делает переименование папок бесплатным.
19. **Дешёвая свёртка.** Для ASCII есть быстрый путь. Остальное один раз проходит через Unicode-разложение при построении индекса. Запрос сворачивается один раз и дальше сравнивается побайтово.
20. **Параллельное построение индекса.** Имена сворачиваются кусками на всех ядрах, сортируются по 8-байтовому префиксу (полное сравнение только при равенстве) и раскладываются параллельно.
21. **Ленивое дополнительное.** Размеры папок и дерево папок для запросов по пути считаются один раз на версию индекса, вне потока интерфейса, до публикации снимка.
22. **Загрузка без копирования.** Файл индекса читается сразу в конечные векторы, контрольная сумма считается по слову, проверяются все инварианты, так что повреждённый или подменённый файл отвергается, а не роняет поиск.

### Поиск

23. **SIMD-поиск подстроки, параллельно.** Блок режется на куски по границам записей, до восьми кусков на поток, чтобы неравномерная плотность совпадений не оставляла ядра без работы. Склеенные результаты остаются отсортированными.
24. **Выбираем самый избирательный терм.** В `foo bar` скан ведёт более длинный литерал, а второй терм проверяется только на кандидатах.
25. **Альтернативы — это сканы, а не проверки.** `a|b` и `ext:jpg;png` запускают по одному скану на ключ и линейно сливают отсортированные списки.
26. **Привязка совпадения к записи «галопом».** Совпадение — это смещение в байтах. Запись ищем, двигаясь вперёд от предыдущей: 1–3 проверки вместо двоичного поиска по всему куску (около четырнадцати).
27. **Плотное ядро AVX2.** Для ключей, которые встречаются очень часто (`a`, `e`), прыжки между совпадениями перестают окупаться. Второе ядро читает по 64 байта за шаг, строит битовые маски первого байта, последнего байта и разделителей `\0`, а номер записи получает через popcount. Когда запись подошла, остальные её кандидаты в блоке пропускаются. Запрос `a` ускорился с 2,0 до 0,4 мс.
28. **Ядро выбираем замером.** Берём восемь окон по 8 КиБ, равномерно по блоку, и переключаемся на плотное ядро только выше 16 000 вхождений на МиБ. Ниже выигрывает memmem (ключ вроде `re` при 6 000 на МиБ на плотном ядре медленнее на 15%).
29. **Отрицание — это дополнение.** `!foo` выполняет обычный быстрый скан для `foo` и выдаёт записи между совпадениями, а не проверяет каждое имя.
30. **Запросы по пути как автомат по сегментам.** Это самый большой выигрыш по одному приёму (2,3 мс → 0,3 мс). Путь — список сегментов. Шаблон `a\b\c` подходит, когда один сегмент заканчивается на `a`, следующий ровно `b`, а за ним идёт сегмент, начинающийся с `c`. Мы один раз обходим дерево папок и храним по одному байту на папку: «путь уже содержит шаблон» плюс «путь заканчивается первыми k частями». Дальше каждый файл решается по байту родительской папки и, редко, одним сравнением префикса. Ни одна строка пути не строится.
31. **Обход дерева в глубину.** Папки пронумерованы так, что каждое поддерево — непрерывный диапазон. Поэтому обход идёт параллельно по поддеревьям, а мелкие поддеревья объединяются в пачки.
32. **Имена папок скопированы в порядке обхода.** Нужные автомату имена лежат в том же порядке, в каком он их посещает: чтение памяти последовательное, без прыжков по блоку на 13 МБ. Только это ускорило запросы по пути примерно на 30%. Состояние занимает 73 КБ на 73 000 папок и помещается в кэш.
33. **Безопасный запасной путь для необычных имён.** Если в имени есть обратная косая черта (возможно в POSIX-пространстве имён NTFS) или в шаблоне больше 7 разделителей, код переходит на проверку полного пути. Оба пути проверены тестами на сравнение с наивной реализацией.
34. **Узкий цикл для частого случая.** Запрос из одного терма-пути обходит общий вычислитель целиком. Срез имени берётся, только если терму он нужен.
35. **Сужение при наборе.** Если новый запрос лишь продолжает прежний (`note` → `notep`), мы фильтруем прошлый результат и не сканируем заново. Набор `notepad` стоит 1,4 мс на все буквы.
36. **Побеждает последний запрос.** Новое нажатие отменяет идущий поиск. Куски проверяют флаг отмены, поэтому устаревшая работа останавливается в пределах одного куска.

### Поведение памяти

37. **Кэш крупных блоков в аллокаторе.** В Windows новый буфер в несколько сотен КиБ получает свежие страницы от системы: отказ страницы и обнуление, около 0,8 мкс на каждые 4 КиБ. Буфер результатов на 1 МиБ стоит 0,2 мс ещё до записи первого id. Небольшой кэш освобождённых блоков (от 32 КиБ до 8 МиБ, не больше 8 МиБ в сумме) делает ту же аллокацию за 15 мкс. После каждой публикации индекса кэш сбрасывается, чтобы не держать бесполезные временные буферы.
38. **Большие результаты заполняются параллельно.** Когда результат велик, потоки пишут свои части в один заранее выделенный буфер вместе, а не один поток копирует всё.
39. **Сливаем, а не сортируем.** Объединение результатов альтернатив — линейное слияние отсортированных списков.
40. **Компактные id.** Результаты — 32-битные номера записей. Имена, размеры и даты берутся только для отрисованных строк.

### Интерфейс и встраивание

41. **Виртуальный список.** В окне список с данными у владельца. Windows запрашивает только видимые строки, поэтому показать 478 000 результатов стоит столько же, сколько 30.
42. **Горячая клавиша без хуков.** Окно создаётся один раз и скрывается. Показывает его `RegisterHotKey`, без низкоуровневого перехвата клавиатуры.
43. **Объединение уведомлений о выделении.** Выделение диапазона порождает тысячи уведомлений. Мы отправляем на все одно обновление строки состояния.
44. **Результаты — неизменяемые снимки.** Поиск держит `Arc` на версию индекса, с которой начал. Живые обновления никогда не блокируют поиск и не меняют его результат на ходу.
45. **JSON пишется вручную.** Сервер и CLI пишут вывод прямо в переиспользуемый буфер. Библиотека разбора работает только на входящих запросах.
46. **Дешёвое встраивание.** DLL выдаёт наборы результатов, привязанные к снимку индекса, и заполняет ваши буферы, так что вызов из C# с поиском и чтением десяти строк стоит 0,26 мс.

### Сборка

47. **Fat LTO, один codegen unit, `panic = abort`, opt-level 3.** Релизный бинарник занимает 0,9 МБ и не имеет зависимостей времени выполнения.
48. **Никаких тяжёлых зависимостей.** На горячем пути только `memchr` (SIMD) и `rayon` (work stealing). Всё остальное — наш код.

### Что мы пробовали или рассматривали и отбросили

* **Поиск на GPU.** Мы его не делали. Один обмен по PCIe по порядку величины равен всему скану на процессоре, выигрывать почти нечего.
* **Сжатие горячей колонки родителей.** Пропустили, опираясь на опубликованный опыт похожих программ: заметно больше процессорного времени и почти никакой экономии памяти.
* **Системная служба.** Она держала бы индекс всегда тёплым, но требует установщика, записей в реестре и процесса SYSTEM. Старт за 20 мс без неё достаточно хорош.
* **Дельта-слой для живых обновлений.** Перестройка занимает 60 мс на пачку при таком размере, поэтому мы выпустили простую версию. Для индексов за 10 млн записей это остаётся в планах.
* **Плотное ядро для всего.** На ключах средней плотности оно проигрывает, поэтому выбирается замером.

## Как проверить наши цифры

```powershell
cargo build --release
.\target\release\usc.exe index           # для чтения MFT нужны права администратора
.\target\release\usc.exe bench           # внутри процесса, 22 запроса, медианы
.\target\release\usc.exe bench-serve     # через JSON-сервер, по 100 строк в ответе
```

От запуска к запуску машины дают разброс 10–15%, поэтому варианты кода надо сравнивать в одном процессе, вперемешку, как мы делали для каждого изменения из этого списка.

## Сборка

Rust 1.88 или новее (edition 2024). Проверено на тулчейне `x86_64-pc-windows-gnu`. Зависимостей на C нет.

```powershell
cargo build --release                        # target\release\us.exe, usc.exe
cargo build --profile release-dll -p us-ffi  # target\release-dll\unthinkable_search.dll
cargo test --release --workspace
powershell -ExecutionPolicy Bypass -File tools\package.ps1   # архивы релиза в dist\
```

## Ограничения

* Windows 10 и 11, x64. Быстрая индексация и живые обновления требуют NTFS. Другие файловые системы индексируются обходом каталогов, без живых обновлений.
* Для чтения MFT нужен один запрос UAC за сеанс. Без него (`us.exe --live off`) программа использует сохранённый индекс или обходит каталоги.
* Размеры папок считают файл с несколькими жёсткими ссылками по разу на каждое имя, поэтому `C:\Windows` получается больше, чем в Проводнике.
* Если живые обновления выключены, изменения попадают в индекс только после переиндексации.
* Горячая клавиша зашита в код. Окна настроек пока нет.
